# cleanmac 的判定机制：什么样的文件可以删

> 一句话：**没有智能识别，只有三层约定——路径白名单、风险分级、可逆删除。**

---

## 为什么不做"智能判断"

"这个文件还有没有用"是语义问题，程序无法可靠回答。任何声称能"AI 识别无用文件"的清理工具，要么在骗人，要么在用启发式规则赌概率——赌输的结果是用户丢数据。

cleanmac 的选择是：**只删那些"按 macOS 约定一定可重建"的东西，其余一律不碰。**

---

## 第一层：规则白名单（看哪里）

`Rule.all` 里手写 11 条规则，每条由 `Target` + `Risk` 组成。`Target` 只有三种形态：

| 形态 | 行为 | 例子 |
|---|---|---|
| `.contents(path)` | 删除目录下所有子项，**保留目录本身** | `~/Library/Caches` |
| `.directory(path)` | 删除目录本身 | `~/.npm/_cacache` |
| `.files(path, exts)` | 按扩展名筛选 | `~/Downloads` 的 dmg/pkg/zip |

判定依据不是文件内容，而是**该路径在系统语义上是否可再生**：

| 规则 | 路径 | 为什么可删 |
|---|---|---|
| CACHE-01 | `~/Library/Caches` | 系统约定的缓存区，App 会重建 |
| CACHE-02 | `…/C/com.apple.appstoreagent` | App Store 下载缓存 |
| WALL-01 | `…/aerials/videos` | 动态壁纸，使用时重新下载 |
| LOG-01 | `~/Library/Logs` | 仅用于排障 |
| DEV-01 | `Xcode/DerivedData` | 编译产物，重新编译即恢复 |
| DEV-02 | `~/.npm/_cacache` | 包缓存，重新安装即恢复 |
| DEV-03 | `~/Library/pnpm/store` | 同上 |
| DEV-04 | `~/.cache/uv` | 同上 |
| DEV-05 | `CoreSimulator/Caches` | 模拟器缓存 |
| TRASH-01 | `~/.Trash` | 用户已明确丢弃 |
| DL-01 | `~/Downloads` 的安装包 | **用户文件，标为谨慎，默认不勾** |

## 第二层：风险分级（默认删不删）

```swift
enum Risk { case safe, careful, risky }
```

代码里只有一个判断：

```swift
selected: rule.risk == .safe
```

**只有 `safe` 默认打勾。** `careful` 和 `risky` 一律不预选，必须用户手动点。

`~/Downloads` 里的安装包虽然是垃圾，但那是用户自己的文件，所以标 `risky`、默认不勾——这个判断比"能不能删"更重要。

## 第三层：隔离区（删错了能不能救）

关键实现细节：**清理路径上一处 `removeItem` 都没有。**

```
cleanSelected()
  → Quarantine.moveRaw()
    → FileManager.moveItem()        // 同卷重命名，毫秒级，不复制数据
    → ~/Library/Application Support/cleanmac/Quarantine/<时间戳>/<序号>-<原名>
    → manifest.json 记录 { original, stored, title, date }
```

还原 = 按 manifest 把文件搬回原路径。

这一层有自测兜底：

```bash
cleanmac --selftest     # SELFTEST OK: move=3 restore=3
```

自测在临时目录造 3 个文件，执行 移动 → 校验源消失 → 还原 → 校验回到原处。**开发中它抓到过一个真 bug**：写 manifest 用 ISO8601 编码日期、读的时候用默认策略解码，导致所有还原静默失败。没有这个测试，就是"清理工具删了东西救不回来"级别的事故。

## 绝对不碰的东西

| 类别 | 路径 |
|---|---|
| 系统只读卷 | `/System`、`/usr`、`/bin`、`/sbin`、`/private/etc` |
| 用户文档 | `~/Documents`、`~/Desktop`、`~/Pictures`、`~/Movies`、`~/Music` |
| 凭据 | `~/Library/Keychains` |
| 云同步目录 | `~/Library/Mobile Documents`、`CloudStorage`（在线占位文件，删了会同步删云端） |
| TCC 保护 | 照片图库、邮件、信息、iPhone 备份（读不到 ⇒ 不处理） |

---

## 边界与已知缺陷

1. **路径约定 ≠ 语义理解。** 无法判断"这份 .psd 还有没有用"，只能判断"这个目录按惯例可重建"。
2. **TCC 盲区。** 照片图库、邮件、备份读不到就当作不存在，界面上标"受保护"，不统计体积。
3. **疑似匹配有误伤风险。** 按目录名反查应用数据时，短键（如 `Code`）只允许全等匹配，长键（≥8 字符）才允许前缀/包含，避免 `Code` 误伤 `CodeBuddy`。
4. **`.localized` 包裹层。** macOS 会把部分应用放进 `Foo.localized/Foo.app`，扫描器需要下钻一层（钉钉就是这种结构）。
5. **需管理员权限的应用**：应用所在父目录不可写时，只能清数据、不能移除本体，界面会标「需管理员」。

---

## 一句话总结

> cleanmac 不判断"你有没有用"，只判断"系统能不能重新造出来"，并且保证**每一步都能撤回**。

## 附录：三种「不可变」不是一回事

删除失败时看到的「不可变」，在 Darwin 里对应三个不同的标志位，可修复性完全不同：

| 标志 | 值 | `ls -lO` 显示 | 谁能设置 | 谁能清除 | cleanmac 的建议 |
|---|---|---|---|---|---|
| `UF_IMMUTABLE` | `0x00000002` | `uchg` | 文件所有者 | 所有者 `chflags nouchg` | 解除锁定后重试 |
| `SF_IMMUTABLE` | `0x00020000` | `schg` | 仅 root | 仅 root `chflags noschg` | 管理员删除（先 noschg 再 rm） |
| `SF_RESTRICTED` | `0x00080000` | `restricted` | SIP | **无人可清** | 不提供方案，如实说明 |

### uchg 从哪里来

最常见的是 **Finder「显示简介」里的「已锁定」勾选框**——它底层就是 `SetFile -a L`，产生的正是 `uchg` 标志（已实测验证）。

其次是：

- `chflags uchg` 手动设置
- 安装器为了让 App 资源不被改动而主动锁定
- 系统组件（例如 Xcode 的 `CoreDevice/DeviceFS` 挂载点）

### 为什么移动会失败

`rename()` 本质是修改目录项并调整 inode 的链接计数，内核在 `unlink`/`rename` 阶段检查 `UF_IMMUTABLE`，命中直接返回 `EPERM`。所以报错是 `Operation not permitted`，而不是「权限不足」那类 `EACCES`。

这也意味着：**改权限位（chmod）没有用，必须清标志位。**

### 检测方式

```bash
ls -lO path              # 第 5 列显示 uchg / schg / restricted
stat -f '%Sf (%Xf)' path # 标志位字符串与原始值
GetFileInfo -ab path     # Finder 属性
```
